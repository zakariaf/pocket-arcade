# Signing and keys

What signs an Android release, where each secret lives, and the one way each is read. The owner never reads code, so these rules are what keeps a key from leaking: never open, print, copy, commit or log the upload key, a password, the service-account JSON or an access token.

## Play App Signing: two keys

| Key | Who holds it | What it signs | If lost |
|---|---|---|---|
| App-signing key | Google (Play App Signing, on by default for new apps) | the APKs Play delivers to phones | cannot be lost by us |
| Upload key | this Mac, `~/.android-keys/<game>-upload.jks` | the AAB we upload; Google checks it and re-signs | the owner asks Google to reset the upload key in the Play Console (App integrity) |

So a leaked or lost upload key is recoverable, but it is still a secret: whoever holds it can upload builds as us.

## The upload key

- Path: `~/.android-keys/<game>-upload.jks` (`uploadKeyPathOf`), outside every repo, mode 600, one key per game.
- Generated by Claude only with the owner's go (decision c of the Android plan, step GP2):

```sh
mkdir -p ~/.android-keys && chmod 700 ~/.android-keys
# two random passwords, generated and passed in this one process's environment, never printed
"/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/keytool" -genkeypair \
  -keystore ~/.android-keys/line-siege-upload.jks -alias upload -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=Applander Upload, O=Applander" -storepass:env E07_UPLOAD_STORE_PASSWORD -keypass:env E07_UPLOAD_KEY_PASSWORD
chmod 600 ~/.android-keys/line-siege-upload.jks
```

  `keytoolGenerateArgs` builds exactly these arguments; the `:env` forms keep the passwords out of the command line and the process list.
- The passwords are written into `~/.gradle/gradle.properties` (mode 600) under the game's own names, by the same process that generated them, and never echoed:

```properties
E07_LINE_SIEGE_UPLOAD_STORE_FILE=<home folder>/.android-keys/line-siege-upload.jks
E07_LINE_SIEGE_UPLOAD_STORE_PASSWORD=<generated>
E07_LINE_SIEGE_UPLOAD_KEY_ALIAS=upload
E07_LINE_SIEGE_UPLOAD_KEY_PASSWORD=<generated>
```

  The names carry the game (`signingPropertyNames`), so no other project on this Mac signs with them, and Gradle reads `~/.gradle/gradle.properties` by itself.
- Checked only by `stat` (`keystoreProblems`: outside the repo, a file, mode 600). The file and `gradle.properties` are never opened by any tool of ours.

## How the release build is signed

React Native's template signs release builds with the debug keystore. The config plugin `packages/shell/plugins/with-upload-signing.ts` (listed in `withShell`'s Android block with `{ game }`) runs `addUploadSigning` on the generated `app/build.gradle`:

- it adds a signing config `upload` that reads the four `E07_<GAME>_UPLOAD_*` properties when they exist;
- release builds use `upload` when `E07_<GAME>_UPLOAD_STORE_FILE` exists, otherwise the debug key (emulator builds and the keyless rehearsal need no upload key);
- it keeps the comment lines React Native 0.86's template puts between `release {` and its `signingConfig signingConfigs.debug` line (a prebuild of Expo SDK 57 writes two);
- it throws at prebuild when the template no longer has the anchors it edits, so a React Native change never silently drops the signing.

A bundle signed with the debug key or unsigned fails `check-store-aab.mjs` rule `signing`; only the keyless rehearsal (`--unsigned`) SKIPs that rule, and it is never release evidence.

## The service-account key

Treated exactly like App Store Connect's `.p8`:

- Path `~/.android-keys/play-service-account.json`, mode 600 (owner step GP3); never pasted into the chat.
- Only `play-credentials.ts` names and reads it (`loadServiceAccount`: stat first, then one read into memory). `check-release-setup-android.mjs` rule `credentials-read` fails any other file that names it.
- The parsed account exposes only the e-mail and a `signRs256` function; the private key stays in its closure, so a log line, `JSON.stringify` or an inspection cannot show it. Parse errors are our own sentences, never the parser's (V8 quotes the input in JSON errors).
- The access token lives in `play-client.ts`'s closure and is sent only as the `authorization` header; errors name the step, the reason and Google's one-line message, never a header.

## What Claude may and may not do

| May | May not |
|---|---|
| `stat` the key files, check their mode and place | open, print, copy, move, hash or commit a key, a password, the JSON or a token |
| generate the upload key with the owner's go | paste a key or a password into a report, a log or the chat |
| run `keytool -printcert -jarfile <aab>` to see who signed a bundle (it reads only the certificate inside the bundle) | `keytool -list` on the keystore (that opens it) |
| delete a key it created by mistake inside the repo, then report it | retry an upload after a 401 or 403 |

`.gitignore` lists `*.jks`, `*.keystore` and `play-service-account.json`, and `.claude/settings.json` denies `Read(~/.android-keys/**)`, `Read(**/*.jks)`, `Read(**/*.keystore)` and `Read(**/play-service-account.json)` (rule `secrets-ignored`; the owner approves edits under `.claude/`). The deny rules are defence in depth; never opening the files is the real guard.

## If a secret leaks

Stop all release work and send the owner one message:

- **Upload key** (in git, a log, the chat): the owner requests an upload-key reset in the Play Console (App integrity, Upload key certificate, Request upload key reset); Claude generates a new key after Google confirms; purge the old file from history only with the owner.
- **Service-account JSON**: the owner deletes that key in the Google Cloud console (Service accounts, Keys) at once and creates a new one (GP3 again).
- **A password**: treat it as the upload-key leak.
